# 2026-06-05 M6 Wireframe Mockups Design

Date: 2026-06-05  
Workspace: `LootingTheLeviathan`

## 목표

M6 구현 예정사항을 설명하는 `와이어프레임 중심` HTML 목업 3종을 만든다.

목업은 실제 게임 화면을 완성 아트로 흉내 내기보다, 구현 우선순위와 화면 판독 구조를 빠르게 검토할 수 있게 해야 한다. 각 목업은 단독 문서로 읽혀야 하며, 화면 위에 `번호형 주석`과 아래 `구현 포인트` 섹션을 함께 제공해 리뷰 문서 역할까지 겸한다.

## 승인된 범위

이번 목업 세트는 다음 3개 화면으로 고정한다.

1. `전투 HUD`
2. `노드맵 + 보상 세레모니`
3. `백팩 정리`

각 화면은 별도 HTML로 작성한다.

## 산출물

구현 단계에서 생성할 파일은 다음과 같이 고정한다.

- `docs/mockups/m6-combat-hud-wireframe.html`
- `docs/mockups/m6-node-map-reward-wireframe.html`
- `docs/mockups/m6-backpack-organization-wireframe.html`

세 파일은 공통 톤을 가지되, 독립적으로 열람 가능해야 한다.

## 왜 분리형 문서 보드인가

승인된 방향은 `분리형 문서 보드`다.

이 방식은 세 화면을 한 문서에 억지로 압축하지 않고, 각 화면의 정보 구조를 충분히 크게 보여줄 수 있다. 또한 이후 하이파이 단계로 올릴 때도 같은 HTML을 확장해 사용할 수 있어 재작업 비용이 낮다.

비채택 대안은 다음과 같다.

- `상태 전개형 단일 문서`
  - 장점: 상태 변화 흐름을 길게 설명하기 좋다.
  - 단점: 한 문서가 지나치게 길어지고, 화면별 수정이 번거롭다.
- `리뷰 보드형 통합 문서`
  - 장점: 세 화면을 한 번에 비교하기 쉽다.
  - 단점: 개별 화면의 주석 밀도와 판독성이 떨어진다.

## 공통 문서 구조

세 HTML 모두 같은 상단 구조를 사용한다.

### 1. 헤더

- 문서 제목
- 한 줄 목표 설명
- 이 화면이 M6에서 무엇을 해결하는지 요약
- `Wireframe`, `Annotated`, `M6` 같은 상태 태그

### 2. 메인 와이어프레임 보드

- 하나의 큰 화면 시안을 중심으로 배치한다.
- 실제 UI 비율을 연상할 수 있도록 `16:9` 기준 보드를 사용한다.
- 완성 아트 대신 패널 윤곽, 구역 구분, 칩, 슬롯, 단계 카드 등 구조물을 보여준다.

### 3. 번호형 주석 레이어

- 화면 위에 `01`, `02`, `03` 식 번호 마커를 배치한다.
- 번호는 우측 또는 하단의 설명 리스트와 1:1 매칭한다.
- 주석은 “무엇이 보이는가”보다 “왜 이 구역이 필요한가”를 설명한다.

### 4. 구현 포인트 섹션

- 이 HTML이 실제 구현에서 무엇을 고정하는지 정리한다.
- 예: read-model 경계, 상태명, cue vocabulary, 반응형 우선순위

### 5. 검토 메모 섹션

- 아직 열린 질문이나 하이파이 단계에서 채울 요소를 짧게 적는다.
- 단, 이번 spec에서는 `TODO` 형태가 아니라 `후속 하이파이 대상`으로 명확히 적는다.

## 공통 시각 원칙

이번 목업은 `와이어프레임 중심`이지만, 완전히 무색 박스만 나열하지는 않는다. 기존 `docs/mockups` 문서 톤을 따라 문서형 프레젠테이션 보드처럼 보여야 한다.

### 유지할 것

- 어두운 바탕 위 카드형 문서 레이아웃
- 큰 중앙 보드
- 얇은 라인과 차분한 포인트 컬러
- 설명 텍스트와 시안이 한 문서 안에서 함께 읽히는 구조

### 의도적으로 생략할 것

- 정교한 텍스처 표현
- 완성형 아이콘 세트
- 실제 게임용 VFX
- 세부 일러스트와 재질 묘사

### 최소한으로 표현할 것

- 에너지/위험/보상 타입 구분용 shape-first 마커
- 패널 우선순위를 보여주는 명암 차
- 경고/선택/활성 상태를 구분하는 선 굵기 또는 점선 처리

## 화면 1: 전투 HUD 와이어프레임

### 목적

`1초 판독`을 기준으로 전투 중 가장 먼저 읽혀야 하는 정보가 어디에 있고 어떤 위계로 보이는지 고정한다.

### 필수 구성

- 상단 또는 상단-좌측의 `Now / Next / Reserve` 큐 구역
- 중앙 전장 보드
- 현재 조준 중인 셀 강조
- 목표 셀과 전면 토큰에 동시에 보이는 약점/미스매치 표시
- 지속 압박을 읽는 `hazard pressure strip`
- `stable -> strained -> critical -> repair required` 순서의 repair ladder
- 간단한 액션 힌트 또는 confirm/cancel 힌트

### 주석이 설명해야 할 포인트

- 왜 `Now`를 가장 크게 보여줘야 하는가
- 왜 전체 큐를 같은 크기의 구슬로 나열하지 않는가
- 왜 weakness/mismatch는 셀과 토큰 양쪽에 동시에 보여야 하는가
- 왜 hazard strip은 위험 순간에만 깜빡이는 경고가 아니라 지속적으로 남아 있어야 하는가
- 왜 repair 표시는 단순 경고 문구가 아니라 단계형 ladder여야 하는가

### 와이어프레임 표현 방식

- 큐는 `dominant chip + compact chip + reserve capsules/count` 구조
- 셀은 단순 격자이되 현재 목표, 위험 셀, 약점 셀을 다른 프레임 처리로 구분
- 우측 패널은 상태 읽기 영역으로 묶고, 숫자보다 단계 이름을 우선 노출

## 화면 2: 노드맵 + 보상 세레모니 와이어프레임

### 목적

한 페이지에서 `경로 판독`과 `보상 리듬`이 어떻게 이어지는지 보여준다. 이 문서는 M6가 단순히 노드 아이콘만 예쁘게 바꾸는 작업이 아니라, 전투 이후의 선택 흐름을 정리하는 작업임을 설명해야 한다.

### 필수 구성

- 상단: 노드맵 패널
- 노드 연결선과 2~3갈래 선택 구조
- 노드별 `risk`, `reward`, `special` 비교 칩
- 하단: 보상 세레모니 패널
- `count_tease -> count_lock -> reveal_queue -> tray_review` 순서 카드
- 현재 단계 강조와 단계별 한 줄 설명
- tray review에서 backpack 정리로 넘어가는 연결 표시

### 주석이 설명해야 할 포인트

- 왜 노드의 정보는 `shape first, color second, text third`로 읽혀야 하는가
- 왜 경로선은 저정보도로 두고 노드 칩을 강조하는가
- 왜 count excitement와 rarity excitement를 분리하는가
- 왜 tray review 이전에는 입력이 잠겨 있어야 하는가

### 와이어프레임 표현 방식

- 상단 노드맵은 실제 게임보다 단순한 도식으로 표현하되, 세 갈래 비교가 가능해야 한다.
- 하단 보상부는 단계 카드 4개를 시간축처럼 배열한다.
- reveal queue는 한 장씩 공개되는 구조가 느껴지도록 중앙 포커스 카드와 보조 pip를 포함한다.

## 화면 3: 백팩 정리 와이어프레임

### 목적

아이템 판독과 배치 판단이 어떤 구획에서 이루어지는지 보여준다. 이 문서는 `Backpack Hero`식 compartment readability를 참고하되, 현재 프로젝트의 핀/시너지/정리 흐름을 설명해야 한다.

### 필수 구성

- 좌측: 획득 아이템 트레이 또는 대기 아이템 구역
- 중앙: 백팩 그리드
- 우측: 핀, 시너지, 규칙, 비교 정보 패널
- 하단 또는 모서리: rotate, place, discard, pin 관련 조작 힌트
- 강조된 슬롯 예시와 점유된 블록 예시

### 주석이 설명해야 할 포인트

- 왜 슬롯 자체보다 `구획`이 먼저 읽혀야 하는가
- 왜 아이템 상세 텍스트보다 실루엣/크기 판독이 우선이어야 하는가
- 왜 핀 정보는 아이템 정보와 분리된 안정 패널이어야 하는가
- 왜 정리 화면에서는 과한 화면 전체 VFX를 피해야 하는가

### 와이어프레임 표현 방식

- 그리드는 단순 사각 슬롯으로 보여주되, 배치된 아이템은 2x1, 2x2, L형 같은 블록 실루엣으로 표현
- 우측 패널은 `Pinned`, `Synergy`, `Placement Notes`처럼 성격이 다른 작은 섹션으로 나눈다.
- 트레이와 백팩 사이 이동 방향을 화살표 또는 흐름선으로 가볍게 표현한다.

## 반응형 원칙

이 HTML은 정적 문서지만, 데스크톱과 좁은 폭에서 모두 무너지지 않아야 한다.

- 데스크톱: 큰 와이어프레임 보드 우선
- 태블릿 이하: 주석 리스트를 보드 아래로 내린다.
- 작은 폭: 좌우 2열 설명을 1열로 쌓되, 보드 자체는 축소 유지

목업 구현은 반응형 앱이 아니라 `검토용 문서`이므로, 모바일에서 완벽한 인터랙션보다 `읽을 수 있는 재배치`를 우선한다.

## 구현 포인트 공통 규칙

- 각 HTML은 단독 파일로 동작한다.
- 외부 자산 의존 없이 HTML + CSS만으로 기본 구조를 표현한다.
- 주석 번호는 DOM 순서와 설명 순서가 일치해야 한다.
- 화면 위 설명 문구는 구현 계획의 용어와 맞춘다.
  - `Now / Next / Reserve`
  - `hazard pressure strip`
  - `repair ladder`
  - `count_tease`
  - `count_lock`
  - `reveal_queue`
  - `tray_review`
- 각 문서 하단에는 `Implementation Notes`와 `Open Questions`를 분리해 넣는다.

## 테스트와 검토 기준

구현 단계에서 확인해야 할 최소 기준은 다음과 같다.

- 세 HTML이 모두 독립적으로 열린다.
- 세 HTML이 모두 공통 문서 톤을 유지한다.
- 번호형 주석과 설명 리스트가 명확히 매칭된다.
- 화면 구성 요소가 M6 refresh plan의 핵심 체크포인트를 빠뜨리지 않는다.
- 좁은 폭에서도 주석과 보드가 겹치지 않는다.

## 최종 결정

승인된 구현 방향은 다음과 같다.

- `전투 HUD`, `노드맵 + 보상`, `백팩 정리`를 각각 별도 HTML로 만든다.
- 세 문서는 `분리형 문서 보드` 형식을 사용한다.
- 시안 밀도는 `와이어프레임 중심`으로 유지한다.
- 각 문서에는 `번호형 주석`과 `구현 포인트`를 포함한다.
- 실제 HTML 구현은 이 spec 리뷰 승인 후 시작한다.
